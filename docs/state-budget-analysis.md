# 状态预算分析：元件相（中继器 / 比较器 / 侦测器）该怎么表示

> 回答一个问题：**在不引入方块实体、也不让运行时开销失控的前提下，能不能把"相"的状态数继续往上加？**
>
> 结论：
> 1. **能，但必须先改表示法**。当前 `phase`（24 值）已把 1.21.11 推到 51.2 万状态 / 506 MiB 堆。
> 2. **不要按 `docs/milestone-2.5-repeater-proposal.md` 的"追加三个独立属性"开工**：
>    `20,976 × 24 × 33 × 17 × 13 ≈ 36.7 亿` 状态，越过 `int` 状态 id 空间，**不是慢，是起不来**。
> 3. **推荐路线（下文的 B2）：把全部元件参数并进 `phase` 一个属性的取值域（84 值），
>    并把宿主收窄到真正能放元件的方块。**
>    总状态 51.2 万 → 81.3 万（+59%），堆 506 → 730 MiB（+44%），注入 ≈34 s（相对原版；
>    比现状多 ≈13 s）；不新增属性、不引入新运行时机制（"按方块裁剪取值子集"是纯机械改动，见 §3.4）。
> 4. 若判定"任意宿主都必须能放元件"，才需要 per-section 稀疏旁路表（Fluidlogged 那套，下文的 A / C），
>    内存反而能降到今天的 50–60%（319 / 257 MiB），代价是同步/序列化/渲染/光照一整套新面积（§6）。
>
> 📖 **A / B1 / B2 / C / D 这些标签是什么、在哪看**：见 §3 开头的“标签对照”表
> （每行一句话 + 数据放哪 + 状态数），§3.1 是完整数据表，§3.3 是逐方案取舍。

数据分两类，逐处标注：**实测**（1.21.11 + `dist/liquidphase-0.1.12+1.21.11.jar`，方法见 §7）
与**估算**（按原版属性表推算，误差来源见 §3.2）。

## 2. 状态数算式（先把口径钉死）

BlockState 的属性是**相乘**的。记：

- `N` = 全部方块的基础状态数合计（不含 `phase`）
- `B` = 全部相容宿主的基础状态数合计（不含 `phase`）
- `V` = `phase` 的取值数（含默认值 `none`）

```
总状态数   = (N − B) + B × V
新增状态数 = B × (V − 1)
堆增量    ≈ 新增状态数 × 779 B
注入耗时   ≈ 新增状态数 × 43.5 µs
```

1.21.11 实测反解：`N = 29,671`、`总 = 512,119`、`V = 24`
→ `23B = 482,448` → **`B = 20,976`**（`N − B = 8,695` 个非宿主状态）。

**多属性是连乘，不是连加。** 这是 §5 那组错误数字的根源。

### 2.1 三个属性一起上会怎样

```
三个独立属性并存：8,695 + 20,976 × (24 × 33 × 17 × 13) ≈ 36.7 亿
```

`Block.BLOCK_STATE_REGISTRY` 是 `IdMapper`，id 是 `int`；**36.7 亿越过 2^31**，
`PalettedContainer` 的位宽、`ClientboundBlockUpdatePacket` 的 `idMapper` 编解码全部失效。
即使**只做中继器**（`24 × 33 = 792`）也是 **1,662 万状态 / ≈12.2 GiB 堆 / ≈12 min 注入**。

### 3.3 A / B1 / B2 / C / D 的具体取舍

**B1 / B2（推荐，风险最低）**：`phase` 从 24 值扩到 84 值，取值互斥（一格只有一个相），**不新增属性**：

```
1  none
7  lava, obsidian, ice, frosted_0..3
16 redstone_0..15
32 repeater   = facing 4 × delay 4 × powered 2
16 comparator = facing 4 × mode 2 × powered 2
12 observer   = facing 6 × powered 2
= 84
```

- B1（全宿主统一 84 值）：**506 MiB → 1.4 GiB（+185%）**，注入 ≈76 s（相对原版）。
  零代码改动，只需扩枚举 + 重跑生成器。
- B2（按方块裁剪，白名单 = 楼梯 + 台阶 5,012）：**506 → 730 MiB（+44%）**，
  注入 ≈34 s（相对原版；比现状多 ≈13 s）。非元件宿主保持 24 值。
- 相对提案的 +12.2 GiB 是两个数量级的差别。
- 零新机制模块：状态注入器、blockstate 生成器、自检、握手、渲染层、存档/网络同步**全部沿用**。
  B2 唯一的额外改动是"属性实例按方块查表"（§3.4）。
- **宿主收窄不是妥协，而是语义必然**：元件要贴在上表面，需要足迹内存在 `h < 1` 的空腔列
  （沿用提案 §2.2 的放置前提）。栅栏/墙/铁栏杆/玻璃板/锁链的顶面是破碎顶点云、没有可用平面，
  树叶顶面被自身模型占满——**这些宿主本来就不该放元件**。楼梯、台阶、完整方块才是真需求。
- B2 的白名单 = 楼梯 58 + 台阶 62 = **5,012 基础状态**（占 `B` 的 24%）。
  要放开到"完整方块"类，把对应 id 加进白名单即可，代价按 `新增基础状态 × 60 × 779 B` 线性预估
  （`60 = 84 − 24`）。
- **中继器的 `locked` 属性**（1.21.1+，被侧向中继器锁存时显示锁形）：完整复刻则 repeater 变 64、
  合并枚举变 **116** 值（B2′，849 MiB）。只做"逻辑锁定、不显示锁形"也是可接受的降级，
  但要在 README 写成已知限制——**不要**悄悄少一个视觉状态。

### 3.4 B2 的额外改动：属性实例按方块查表

B1 里全部宿主共享同一个 `PhaseHelper.PHASE` 实例；B2 要让不同方块拿到不同取值数，
必须**每个方块（或每组方块）建一个同名属性实例**：

```java
// 现在：单例
public static final EnumProperty<Phase> PHASE = EnumProperty.create("phase", Phase.class);

// B2：按方块查表（注册期建好并缓存）；getPhase 仍对"没有该属性"的状态返回 NONE
public static EnumProperty<Phase> phaseOf(Block block) { ... }
public static Phase getPhase(BlockState state) { ... }
```

影响面（全部是机械替换，不引入运行时机制）：
`withPhase` / `getPhase` / `canAcceptPhase` / `meltedState`、`PhaseRenderSupport.hasPhase` /
`hostState`、`ShapeFallbackMixin`、`WallBlockShapeMixin`、`RedstoneBlocks`、
`PhaseStateRefresher` 的入参、`tools/gen_phase_blockstates.py` 的条件生成、
自检里"每个取值都有 part"与"每个宿主都有 phase 属性"两组断言。

> ⚠️ 属性实例**必须同名**：`EnumProperty.create("phase", …)` 的 `name` 一致，
> blockstate JSON 的 `"phase": "…"` 条件才能被所有宿主共用同一套语法；
> 取值子集的差异只体现在"这个方块的状态里有没有这个值"。
> 若改成不同属性名（`phase_a`/`phase_b`），生成器要写两套条件，`/setblock` 的语法也会分裂
> ——**不要这么做**。

> ⚠️ **同名属性实例之间 `equals` 为真**（`Property.equals` 只比 `clazz` + `name`，
> 六版本一致，已核对 guardian）。但**状态值表的查找方式随版本不同**，这会让"用错实例"
> 变成**跨版本不一致的静默 bug**：
>
> | 版本 | `StateHolder.values` | 查找语义 | 用错实例的后果 |
> | --- | --- | --- | --- |
> | 1.19.4 / 1.20.1 | `ImmutableMap` | `equals` + `hashCode` | `hasProperty` 返回 **true**、`getValue` 拿到该方块自己的值——**看起来能跑**；但 `setValue` 走 `neighbours.get(property, value)`（Guava `Table`，同样按 `equals` 索引），会命中同名属性的邻居表，所以在本 mod 的用法下**通常也对**，只是把"取值子集"的边界悄悄绕过了 |
> | 1.21.1 / 1.21.10 / 1.21.11 / 26.3 | `Reference2ObjectArrayMap` | **身份比较**（`findKey` 用 `==`） | `hasProperty` 返回 **false** → `getPhase` 退成 `NONE`，**写入静默丢失** |
>
> 所以 B2 里**所有** `withPhase` / `getPhase` 都必须从 `state.getBlock()`（或该方块自己的
> `StateDefinition`）取属性实例，绝不能缓存一个"全局 `phase` 属性"再到处用；
> `PhaseStateRefresher.addBlockProperty` 的 `property` 入参也必须是"给这个方块新建的实例"。
> **这条无法靠编译期发现**，必须靠自检兜住：
> 对每个 `PhaseCapable` 方块，遍历 `phaseOf(block)` 的全部取值做
> `defaultBlockState().setValue(phaseOf(block), v)` 且 `getPhase()` 读回等于 `v`，
> 任一失败即报错；另加一条"对 A 方块的实例问 B 方块的状态必须返回 false"的反向断言
> （只在 1.21.1+ 成立，1.19.4/1.20.1 需要按 `equals` 语义放行）。
>
> 正因为这条差异，**B2 的验收必须在六个版本上都跑一遍**，不能只在 1.21.11 验证。

**A / C（旁路表，能力最强、机制最重）**：状态里只留"相/元件类别"（8–12 值），
全部参数（朝向/延迟/模式/功率）放进 per-section 稀疏表。内存是**所有方案里最低的**
（319 / 257 MiB，比今天还少 37–49%），并且支持全宿主 + 任意参数。

- 真正的成本不在内存，在 §6 那七行面积：区块序列化、section 网络包、渲染期查表、
  光照/流体/刻的三个无坐标入口、Sodium 兼容。
- 这个仓库旁边的 `Fluidlogged/` 就是这套机制的完整参考实现，**同时也是"要做多少个 mixin"的清单**。

**D（语义简化，最后的降档手段）**：把"含红石相的宿主"从"线"退化成"红石块"——
**不存功率，恒为 15**。16 → 1 个取值，新增状态降到今天的 **35%**（482k → 168k），
堆 506 → 272 MiB，信号查询变 O(1)（不再有 −1 衰减链）。这是**产品语义决策**：
好处是彻底摆脱"功率必须驻留"这个最贵的约束；坏处是与红石线的衰减/方向语义不一致，
而规划 §3.4 明确要求衰减。建议作为配置项保留，而不是默认。

### 4.1 有些入口原版不给你坐标

这是当前实现最大的"隐形红利"。下面这些方法**签名里没有 `BlockPos`**，却被原版在热路径上调用；
只要数据在状态里，它们就是零成本：

| 入口 | 签名 | 当前靠什么 | 旁路表方案的后果 |
| --- | --- | --- | --- |
| `getFluidState()` | 无 pos | `phase==LAVA → 熔岩源` | 必须改 `LevelChunkSection.getFluidState`、流体刻计数 |
| `getLightEmission()` | 无 pos | `phase==LAVA → 15` | 必须改 `BlockLightEngine`（Fluidlogged 的 `BlockLightEngineMixin` 就是干这个） |
| `isRandomlyTicking()` | 无 pos | `phase==LAVA/ICE` | section 的 `tickingBlockCount` 靠它算，必须逐 section 叠加旁路计数 |
| `getRenderShape()` | 无 pos | 带相 → 强制 MODEL | 必须在渲染期按坐标查旁路表 |
| `isSignalSource()` | 无 pos（1.21.11 状态级） | 带相 → true | 红石线连接判定会漏（线只连 `isSignalSource` 的方块） |
| `Cache.collisionShape` | 构造期预计算，之后 `getCollisionShape(level,pos)` 直读 | 固相 = 整格 | 必须在每次 `getCollisionShape` 查表（碰撞是最高频调用之一） |

**凡是"位置相关"的数据搬到旁路表，这六处就要逐个改调用点**，而不是"加一个 mixin 就完事"。

### 4.2 红石功率必须驻留，不能每次重算

两个含红石相的宿主互相读数；若功率靠"现场递归算邻居"，查询就是 O(链路长度)，且互相触发。
原版红石线把 `POWER` 放进状态，正是为了把查询压成 O(1)。

所以功率只有两个去处：**状态里**（贵内存，零机制）或**旁路表里**（省内存，贵机制）。
**不存在"都不要"的第三选项。** 这也是方案 B1/B2 把 16 个功率档全部留在状态里的原因。

### 4.3 状态数是乘积，而且已经有一块浪费但省不掉

`withPhase` 强制"`waterlogged=true` ⟺ `phase=none`"，双台阶也不可能含相——粗估 51 万里
约 40% 是**不可达状态**。理论上把 `waterlogged` 折进 `phase` 能省近一半，但 `waterlogged` 是
原版到处在用的属性（`SimpleWaterloggedBlock`、`getFluidState`、`updateShape`、
`getStateForPlacement`、其他 mod 的兼容假设），**不能动**。这笔钱只能认，
它也是"别再加属性"的又一个理由。

## 5. 提案文档里的算术错在哪

`docs/milestone-2.5-repeater-proposal.md` §2.1 原文：

```
每宿主状态数 = 原宿主状态数 × 33   （只做中继器）
每宿主状态数 = 原宿主状态数 × 63   （三个元件全开：33+17+13 个非默认值）
即：仅中继器 ≈ 现有 phase 开销的 4.1 倍（33/8），三个元件全开 ≈ 7.9 倍（63/8）
```

四处问题：

1. **漏乘了现有的 ×24。** `phase` 自 0.1.5 起是 24 值，不是 8。所以"仅中继器"是 **33 倍**于新增状态（不是 4.1 倍），总量 1,662 万。
2. **`63 = 33+17+13` 只在"三者合并进同一个互斥属性"时成立，而方案本身写的是三个独立属性。**
   三个独立属性的组合数是 `33×17×13 = 7,293`。**表示法与算式自相矛盾**，按表示法算就是 36.7 亿、`int` 溢出。
3. **"合并三元只省 2 个状态"是反的。** 合并把 `7,293` 组合压成 61（提案口径）或含红石相/固相的
   **84**（本 mod 实际口径），省掉 **99.2%**。它不是"可选优化"，是**唯一可行前提**。
4. **示例表里的 `×8` 也应改成 `×24`**（该表已过时）。

正确对照（基础状态数见 §3.2，`V=84` 为并集方案）：

| 宿主 | 基础状态 | 现状 `×24` | 提案 `×24×33` | 提案 `×24×63` | **并集 `×84`** |
| --- | --- | --- | --- | --- | --- |
| 楼梯 | 80 | 1,920 | 63,360 | 120,960 | **6,720** |
| 台阶 | 6 | 144 | 4,752 | 9,072 | **504** |
| 栅栏 | 32 | 768 | 25,344 | 48,384 | **2,688** |
| 墙 | 324 | 7,776 | **256,608** | 489,888 | **27,216** |

> 注意 `×24×63` 这一列本身也是错的（见问题 2）：它假设三者可以共存又用加法，
> 所以只作"原稿口径"的展示，不是任何可行方案的估算。真实的三属性方案是 `×24×7,293`。

## 6. 若要全宿主支持元件：旁路表的真实成本

如果最终判定"任意相容宿主都应能放元件"，只能走 A/C。成本清单（都有 Fluidlogged 现成参考）：

| 面积 | 要做的事 | 参考位置 |
| --- | --- | --- |
| 存储 | `LevelChunkSection` 挂 `Short2ObjectOpenHashMap`（键 = `x<<8\|y<<4\|z`，short） | `Fluidlogged/.../LevelChunkSectionMixin.java` |
| 存档 | `ChunkSerializer.read/write` 里 palette + `int[]`（`(pos<<16)\|id`），`LocalCapture` 取 section | `.../ChunkSerializerMixin.java` |
| 网络 | 自定义 section 包 + `ChunkHolder` 的 changed-set 广播 | `.../ChunkHolderMixin.java`、`ClientboundSectionFluidsUpdatePacket` |
| 渲染 | `RenderChunk` 快照 + `RenderChunkRegion` 转发 + `RebuildTask` 按坐标查表 | `.../RenderChunkMixin.java`、`RenderChunkRegionMixin.java`、`RebuildTaskMixin.java` |
| 光照/流体/刻 | 见 §4.1 的六处 | `.../BlockLightEngineMixin.java`、`LevelMixin.java` |
| Sodium | `ClonedChunkSection` / `WorldSlice` 各一层 | `.../compat_sodium/*` |
| 一致性 | `setBlockState`、活塞移动、`/setblock`、世界生成、区块拷贝时的表清理 | `LevelChunk` 的 setBlockState 路径 |

存储本身几乎免费（每格 2 B 键 + 1 B 值，且稀疏），**贵的是上面七行面积**，
以及"方块状态变了但 section 表没跟着清"这类一致性问题。相对地，方案 B1/B2 的一致性由原版
状态机本身保证——这是本项目最该珍惜的性质：0.1.1–0.1.12 修的几乎全是渲染/注册/同步类 bug。

## 7. 复现方法

实测在临时目录做（不写进仓库）：复制 `test-server/1.21.11`，删掉 `world/` `logs/` `crash-reports/`，
`mods/` 只留 `fabric-api-*.jar` 与 `dist/liquidphase-0.1.12+1.21.11.jar`，`server.properties` 改
`level-name=benchworld`。脚本逻辑：

```powershell
java -Xms512M -Xmx3G -jar fabric-server-launch.jar nogui     # 后台起服
# 轮询 logs/latest.log 等 "Done ("
jcmd <pid> GC.run
jcmd <pid> GC.heap_info
jcmd <pid> GC.class_histogram
# 输入 "stop" 正常关服
```

对比项：`config/liquidphase.json` 的 `phaseEnabled` 置 `false` / `true` 各跑一次，
`total states` 取日志里的 `injected phase property into N blocks (total states: M)`。

**注意**：
- 不要在 `runClient` 里估这部分内存——客户端纹理/模型缓存会淹没差异，且 `BlockStateModel` 是
  **懒烘焙**的，只有真正渲染到的状态才建模型。本文只测服务端；而服务端的 51 万状态是**双端都要付**的。
- 耗时不可靠、只给量级：重跑观察到注入段 **21–55 s**、`Loading→Done` **22–60 s**。
  内存可靠：两次独立运行的 `GC.heap_info` used 为 518,297 KB 与 519,656 KB（差 1.3 MiB，≈0.25%）。
  **线性外推只用内存口径。**

## 8. 结论与待办

1. **不要按提案的三独立属性方案开工**：`×24×33×17×13` 会越过 `int` 状态 id 空间。
2. **推荐方案 B1 起手、按需升级到 B2**：`phase` 扩到 84 值（互斥取值）。
   B1 全宿主统一、零代码改动，506 MiB → 1.4 GiB；B2 按方块裁剪取值子集
   （白名单 = 楼梯 + 台阶 5,012 基础状态），506 → 730 MiB，
   代价是要把 `PhaseHelper.PHASE` 单例改成按方块查表（§3.4）。
   要放开宿主就按 `新增基础状态 × 60 × 779 B` 加预算。
3. **任何新"相"都不许新增属性**，只能进 `phase` 的取值域。建议把这条写进 `AGENTS.md` §7，
   并附上 `总状态数 = (N − B) + B × V` 与 1.21.11 的 `B = 20,976` 口径。
4. **配套断言**（都属"清单类"回归，历史上反复踩）：
   - 每个宿主 `基础状态数 × V ≤ 预算`（建议 8,000/方块；墙在当前 24 值下就已 7,776，扩值前必须先裁）；
   - `phase` 的**每一个取值**在该宿主的 blockstate 里都有对应 part；
   - 注入后的总状态数与生成器/自检的期望值**双向**一致（少一个 = 含相看不见，多一个 = `Unknown property`）；
   - 新增取值时同步 `Phase` 的区间判断。**当前的 `isRedstone()` 是
     `ordinal() >= REDSTONE_0.ordinal()`，没有上界**——把元件取值追加在 `redstone_15` 之后，
     `repeater_*`/`comparator_*`/`observer_*` 会被判成红石相（`redstonePower()` 返回 16 以上，
     红石外壳/信号都会错）。必须改成显式上界或 `switch`；`isSolid()` / `isFrosted()` 同理
     （见 AGENTS.md §7 第 6 条）。
5. 若将来内存仍是瓶颈，**D 是唯一能大幅降档的产品级手段**（红石相退化为满功率源，16 → 1 值），
   应做成配置项而非默认行为。
6. 若将来必须全宿主支持元件，走 C，并把 §6 的七行面积明确写进 README 的已知代价，
   同时在 `tools/` 里加一条"旁路表 ↔ 方块状态一致性"的自检。
